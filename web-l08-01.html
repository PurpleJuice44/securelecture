웹 Level 8 장(chapter)

JWT 취약점

토큰 구조와 서명 검증 실패 사례를 배운다.

⚠️ 실습은 본인 소유 VM·실습용 사이트(허가된 환경)에서만 수행하세요.

1. 학습 목표

  • header.payload.signature 구조
  • alg=none 위조, 약한 secret 브루트포스
  • 만료 검증 누락 시 리플레이 위험

2. 핵심 개념

  • header.payload.signature 구조
  • alg=none 위조, 약한 secret 브루트포스
  • 만료 검증 누락 시 리플레이 위험

2-2. 동작 원리 심화: 도장이 깨지는 순간

JWT는 헤더·페이로드·서명 3부분의 점찍기 문자열입니다. 서버는 서명으로 위조를 가려내야 하는데, 검증 로직에 구멍이 있으면 공격자가 페이로드를 마음대로 고칩니다.

flowchart TD T["JWT 수신"] --> A{"alg 확인"} A -->|none 허용| F["서명 없이 수락
치명적"] A -->|RS→HS 혼동| K["공개키로 HMAC 검증
위조 가능"] A -->|정상| V["서명 검증"] V --> E{"만료·발급자 검사"} E -->|누락| R["무한 재사용"] E -->|정상| OK["사용자 복원"]

읽는 법: 서명 검증→클레임 검사의 2관문입니다. 어느 하나라도 비어 있으면 토큰은 종이 도장과 같습니다.

2-3. 취약점 3종

취약점원리대응
alg=none서명 생략 허용허용 alg 화이트리스트
약한 secret사전 대입으로 서명 가능긴 난수 secret·주기 교체
만료 미검증탈취 토큰 무한 재사용exp 필수 검사+짧은 유효기간

3. 예제

jwt.io에서 토큰을 디코딩해 3부분을 구분해본다

3-2. 심화 예제: 검증 체크리스트(실습 앱)

# 1) 3부분 분리 후 페이로드 판독
echo $TOKEN | cut -d. -f2 | base64 -d 2>/dev/null
# 2) alg=none 변조 토큰 수락 여부 (서명부 비움)
# header {"alg":"none"} + payload + "." 로 요청 → 200인가?
# 3) 만료 변조: exp를 과거로 바꾼 토큰 요청 → 거부되는가?
# 4) secret 강도: jwt-cracker 계열로 사전 대입(실습 키만)

4. 실습

  1. 만료 시간을 변조한 토큰의 수락 여부를 테스트(실습).
  2. alg=none 변조 토큰을 만들어 서버 반응을 기록한다.
  3. 페이로드의 role을 바꿔 권한 상승 여부를 확인한다.
  4. 서버 검증 로직(alg 목록·exp 검사)을 코드로 찾아낸다.
  5. 대응 패치 후 2·3번을 재시험한다.

5. 퀴즈

  1. 서명 검증이 실패하면 서버가 해야 할 일은?
  2. secret이 약하면 생기는 일은?
  3. JWT를 복호화하면 내용이 보이는 이유는? 암호화와 다른 점은?
  4. 만료 검사를 빼먹으면 생기는 일은?
  5. 리프레시 토큰을 쓰는 이유는?
정답 보기
  1. 즉시 거부(401)하고 로그를 남긴다. 부분 수락은 없다.
  2. 공격자가 secret을 맞춰 임의 페이로드에 서명해 관리자 토큰을 찍어낸다.
  3. 서명은 무결성 보장용이라 본문은 base64일 뿐 암호화가 아니기 때문이다. 민감정보를 넣으면 안 된다.
  4. 탈취된 토큰이 영원히 유효해 로그아웃·변경이 무의미해진다.
  5. 짧은 액세스 토큰+긴 리프레시로 탈취 피해를 줄이고 재발급을 통제하기 위해서이다.

5-2. 한눈에 보는 검증 순서

sequenceDiagram participant B as 브라우저 participant S as 서버 B->>S: JWT 제시 S->>S: alg 화이트리스트 확인 S->>S: 서명 검증 S->>S: exp·iss 검사 S-->>B: 사용자 복원 또는 401

읽는 법: alg→서명→클레임 순서로 하나라도 실패하면 즉시 401입니다. 통과한 뒤에야 사용자 정보를 믿습니다.

6. 흔한 실수

  • 서명 검증 없이 페이로드를 신뢰하는 경우. sub·role은 주장일 뿐이다.
  • 민감정보를 페이로드에 넣어 토큰 유출=정보 유출이 되는 경우
