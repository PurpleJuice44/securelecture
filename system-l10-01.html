시스템 Level 10 장(chapter)

시스템 프로젝트

하드닝+진단 보고서를 포트폴리오로 만든다.

⚠️ 실습은 본인 소유 VM·실습용 사이트(허가된 환경)에서만 수행하세요.

1. 학습 목표

  • 취약 VM 1대 선정(실습용)
  • 진단→조치→재점검 사이클
  • 전후 비교 보고서

2. 핵심 개념

  • 취약 VM 1대 선정(실습용)
  • 진단→조치→재점검 사이클
  • 전후 비교 보고서

2-2. 동작 원리 심화: 진단→조치→재점검 사이클

프로젝트는 한 번 진단하고 끝이 아니라 사이클입니다. 취약 VM을 골라 진단하고, 조치하고, 다시 점검해 전후를 비교합니다. 전후 비교표가 포트폴리오의 심장입니다.

flowchart TD S["대상 선정
실습용 취약 VM"] --> D["진단
점검표 작성"] D --> M["조치
하드닝 적용"] M --> R["재점검
동일 항목"] R --> C["전후 비교
개선 증명"] C --> P["포트폴리오 정리"]

읽는 법: 재점검이 없으면 조치가 됐는지 알 수 없습니다. 사이클을 한 바퀴 돌려야 완성입니다.

2-3. 전후 비교표 양식

항목조치 전조치 후
SSH 인증비밀번호 허용키인증 전환
방화벽전체 허용SSH만 허용
SUID불필요 3개제거 완료

3. 예제

조치 전/후 점검표 비교

3-2. 심화 예제: 프로젝트 산출물 목록

# 산출물 체크리스트
# 1) 진단 보고서 (자산·점검표·위험도)
# 2) 조치 기록 (명령·출력·시각)
# 3) 재점검 결과 (동일 항목 전후 비교)
# 4) 잔여위험 + 향후 계획
# 포인트: 스크린샷마다 명령·목적이 보이게 캡처한다

4. 실습

  1. 프로젝트 보고서를 작성한다.
  2. 대상 VM과 범위를 문서화한다.
  3. 진단→조치→재점검을 한 사이클 돌린다.
  4. 전후 비교표를 채운다.
  5. 잔여위험과 다음 계획을 적는다.

5. 퀴즈

  1. 재점검의 의미는?
  2. 포트폴리오에 남길 것은?
  3. 전후 비교가 필요한 이유는?
  4. 잔여위험을 적는 이유는?
  5. 좋은 프로젝트의 조건은?
정답 보기
  1. 조치가 실제로 됐는지 같은 잣대로 확인하는 것이다.
  2. 과정·근거·결과가 담긴 보고서이다.
  3. 개선 효과를 증명해야 하기 때문이다.
  4. 숨기지 않고 관리해야 신뢰되기 때문이다.
  5. 재현 가능하고 정직한 것이다.

5-2. 한눈에 보는 마무리

sequenceDiagram participant A as 작성자 participant R as 검토자 A->>R: 보고서 제출 R-->>A: 재현·근거 보완 A->>R: 전후 비교 확정 R-->>A: 공개 승인

읽는 법: 검토는 문장이 아니라 재현 가능성을 봅니다. 전후 비교가 있으면 설득력이 배가됩니다.

6. 흔한 실수

  • 조치만 하고 재점검을 빼먹는 경우
  • 잔여위험을 숨기는 경우. 드러내는 것이 신뢰이다.
